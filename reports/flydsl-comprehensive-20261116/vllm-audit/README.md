## Operations and numerical behavior

- **Previous W4A4 emulation:** dynamic MXFP4 quantize/dequantize the BF16 activation; dequantize packed MXFP4 weights using block E8M0 scales (each block covers 32 values); call `torch.nn.functional.linear` in the activation dtype, normally BF16. Unless `VLLM_MXFP4_EMULATION_DEQUANT_AT_LOAD=1`, weight dequantization happens each invocation. With that flag, weights are converted once at load and the linear uses the dense copy.
- **FlyDSL W4A8:** preserve the packed MXFP4 checkpoint weights. `prepare_weights` pads output rows to 16, arranges nibbles/scales, then selects lossless E4M3/E5M2 scale folding where possible or grouped scaling otherwise. At each call, vLLM dynamically quantizes each activation row to FP8 E4M3 and provides its FP32 scale. The FlyDSL kernel decodes packed E2M1 nibbles into FP8 weight fragments, performs FP8 WMMA with FP32 accumulation, applies folded/grouped weight and activation scales, and casts to BF16/FP16 output.
- Both paths use MXFP4 weights, but their activation quantizers differ. Treat their output difference as a W4A4-versus-W4A8 numerical delta, not a pure GEMM backend error. For accuracy checks, compare each path against a reference that uses that path's own activation quantization.

## Matched layer timing setup

Use the same packed weights, scales, BF16 input tensor, and `M,N,K` in both arms. Construct separate layer objects because each backend's post-load processing mutates/replaces weights. The cached safetensors blob can supply a real layer for one matching N/K shape. The 1,842-shape sweep uses synthetic weights because it spans unrelated dimensions.

1. Baseline: force `VllmConfig(kernel_config={"linear_backend_per_quant": {"mxfp4": "emulation"}})` and call `init_mxfp4_linear_kernel(kMxfp4Dynamic)`. This preserves the W4A4 activation scheme and matches the historical pre-FlyDSL default implementation.
2. Candidate: use the normal auto selector with `init_mxfp4_linear_kernel(kMxfp4Dynamic)`. On gfx1201, the current selector substitutes `kFp8DynamicTokenSym` for the RDNA4 candidate and returns `Rdna4Mxfp4LinearKernel`. The harness asserts the selected class and activation key.
3. Warm each arm and finish compilation before collecting times. Time the full `apply_weights` for layer cost; if also reporting GEMM-only, clearly separate it from activation quantization. Use synchronized HIP events or graph replay for decode-sized M and report medians plus dispersion across repeated samples.
4. Keep M identical and include representative decode and prefill M values. Record the TP-local N/K, output dtype, cache policy, graph setting, and whether weight dequantization/preparation is inside the measured interval. Validate each arm against its own quantized reference, then separately report W4A4-vs-W4A8 output error.

## GPU1 preflight

The benchmark-only harness passed an isolated synthetic GPU1 preflight on the actual `apply_weights` implementations. Six paired W4A4/W4A8 shapes passed each backend's sampled arithmetic reference, including the odd-N tail `[73,513,4096]` and largest manifest shape `[8192,16384,16384]`. Two shapes ran FlyDSL-only because Quark emulation rejects their dimensions: `[1,16,32]` fails activation QDQ's `M*K % 64` requirement, and `[8,7,160]` fails weight decode's `N*K % 512` requirement. These one-arm rows passed their own-reference and changed-input graph checks; they are excluded from paired speedup comparisons. The full samples, medians, selected configs, and rejection strings are in [preflight-gpu1.json](preflight-gpu1.json).

All weights and activations in this preflight were synthetic; the `[1,17408,5120]` row only matches the cached checkpoint projection dimensions. The checkpoint tensor and full model were not loaded. The preflight used 16 event-timed rounds, with one-time weight preparation outside timing; W4A4 weight decoding and activation quantization stay inside each `apply_weights` call. Graph timing excludes CPU Python dispatch and allocation overhead. The read-evicted protocol reads a 256 MiB buffer and activation tensor before replay. The preflight timing samples were collected before the final timing-loop cleanup removed an intermediate host synchronization between conditioning and the measured graph; treat those values as protocol-debug output, not final comparative performance. The corrected loop queues conditioning and measurement on the same stream and synchronizes after the measured replay.

## Constraints and provenance

FlyDSL requires ROCm, gfx1200/gfx1201, and the adapted `flydsl.kernels.gemm.rdna4_mxfp4` import. Its checkpoint inputs are uint8 packed weights `[N,K/2]` and uint8 E8M0 scales `[N,K/32]`; K must be a positive multiple of 32, N positive, output BF16 or FP16. The Quark emulation kernels have stricter implementation limits: activation QDQ requires `M*K % 64 == 0`, and weight dequantization requires `N*K % 512 == 0`. The emulation kernel needs the `amd-quark` package. Preserve unsupported baseline cases as explicit FlyDSL-only rows; do not pad shapes or calculate a paired speedup for them.

Detailed source and model metadata references, commit IDs, environment caveats, and benchmark constraints are in [evidence.json](evidence.json). No production source files were modified and no full-model inference or complete-checkpoint timing was run.
